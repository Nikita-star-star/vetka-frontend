# Лабораторная работа №2. Состояние и интерактивность

## Цель работы

Превратить статический каталог из первой лабораторной в интерактивное приложение с `useState`, событиями, управляемыми формами, фильтрацией и изменением коллекции без мутации.

## Постановка задачи

Продолжайте **тот же проект и ту же предметную область** из ЛР1. Сохраните работающие карточки, оформление и модель данных. Вместо создания новой страницы реализуйте действия пользователя над существующей коллекцией.

## Исходные данные

Выполнена ЛР1; пройдены лекции 8–15. В проекте есть массив как минимум из 12 объектов и компоненты `App`, `ItemList`, `ItemCard`. Новые зависимости не обязательны. Допускается рефакторинг структуры, но уже реализованный интерфейс должен сохраниться.

## Единая модель проекта

Во всех вариантах предусмотрена коллекция однотипных объектов со стабильным `id`, компонент карточки, компонент списка, минимум два смысловых свойства для отображения и одно условное свойство для статуса. Студент выбирает предметную область **один раз** в первой лабораторной и продолжает **тот же проект** во второй и третьей, сохраняя данные, компоненты и CSS. Менять предметную область между работами нельзя без согласования с преподавателем.

Предметные различия не меняют объём обязательной реализации: каждый студент должен продемонстрировать сопоставимый набор механизмов React. Если в тематике нет естественного аналога корзины или избранного, используется действие «добавить в личный список / удалить из личного списка». Это действие не требует регистрации или серверной базы данных.

## Общие функциональные требования

1. Коллекция хранится в React-state на уровне общего владельца.
2. Пользователь может добавить новую запись через управляемую форму.
3. Пользователь может изменить как минимум одно смысловое свойство записи и удалить запись.
4. Форма проверяет обязательное название и предметно значимое поле; сообщение об ошибке появляется рядом с полем.
5. Поиск по названию работает без перезагрузки страницы.
6. Есть фильтр по одному категориальному или логическому полю.
7. Есть сортировка по предметно значимому свойству.
8. Есть действие по добавлению/удалению записи в персональную подборку, если это подходит теме; иначе — переключение важности/статуса.
9. Показаны число всех объектов и число объектов в текущей выборке.
10. Отображаются отдельные сообщения для пустой коллекции и пустых результатов фильтрации.
11. Все добавления, изменения и удаления должны быть видны в интерфейсе без перезагрузки.

## Технические требования

- Для коллекции, поиска, фильтра, сортировки и формы применён `useState` там, где он действительно необходим.
- Обработчики передаются из владельца данных дочерним компонентам через props.
- Формы работают через `onSubmit` и `event.preventDefault()`; поля имеют `<label>`.
- Массивы и объекты обновляются через создание новых значений (`map`, `filter`, spread), а не через `push`, `splice` или присваивание в старый объект.
- Число найденных элементов вычисляется из массива, а не хранится отдельным state.
- Нельзя переносить управление всей коллекцией внутрь карточки.

## Соответствие предметных областей

| Вариант | Добавление / редактирование | Фильтрация | Сортировка | Дополнительное действие |
|---|---|---|---|---|
| Интернет-магазин | Создать / изменить товар каталога | Категория, наличие | Цена | Добавить в корзину, изменить количество, удалить |
| Планировщик задач | Создать / изменить задачу | Статус, приоритет | Приоритет | Переключить выполненность |
| Каталог фильмов | Добавить / изменить запись фильма | Жанр, избранное | Рейтинг | Добавить в избранное / удалить |
| Библиотека книг | Добавить / изменить книгу | Жанр, прочитано | Автор или год | Добавить в список чтения |
| Платформа мероприятий | Добавить / изменить мероприятие | Категория, запись | Дата | Записаться / отменить запись |
| Каталог курсов | Добавить / изменить курс | Уровень, направление | Продолжительность | Добавить в план обучения |

Обратите внимание: интернет-магазин не обязан реализовывать оплату или складской учёт; платформа мероприятий не требует настоящих билетов. Проверяется React-логика, а не сложная бизнес-система.

## Методические указания

1. Зафиксируйте рабочую версию ЛР1. Не начинайте новый проект.
2. Перенесите исходный массив в `useState` в общем родителе. Продумайте, какие компоненты только читают данные, а какие вызывают изменения.
3. Создайте форму добавления с полями по своей предметной области. Начните с названия и одного дополнительного поля; затем добавьте валидацию.
4. В `App` реализуйте функцию добавления: нормализуйте входные данные, создайте уникальный `id`, верните новый массив через функциональное обновление.
5. Реализуйте удаление через `filter`. Убедитесь, что соседние карточки сохраняют правильные `key`.
6. Реализуйте редактирование через `map` и создание нового объекта для совпавшего `id`. Значения существующих записей не должны пропадать.
7. Добавьте `query` для поиска. При фильтрации используйте `.toLowerCase()` или нормализацию строки только там, где это нужно для сравнения текста.
8. Добавьте категориальный фильтр и сортировку. Сортировку выполняйте на новом массиве, например `[...visibleItems].sort(compare)`, чтобы не мутировать состояние.
9. Разделите компоненты: `ItemForm`, `Filters`, `ItemList`, `ItemCard`. Их точные имена могут быть предметными.
10. Добавьте дополнительное предметное действие. Состояние должно оставаться согласованным: например, товар, удалённый из каталога, не должен выводиться в подборке без продуманного правила.
11. Проверьте несколько последовательных операций: добавить → изменить → отфильтровать → отсортировать → удалить.
12. Проверьте пустой результат и ошибочный ввод. Обновите интерфейс для телефона.

**Подсказка по неизменяемому обновлению:**

```js
setItems((previous) =>
  previous.map((item) =>
    item.id === targetId ? { ...item, active: !item.active } : item
  )
);
```

Этот фрагмент демонстрирует механизм обновления одного поля, но не является полным решением проекта. Не используйте `useEffect` для вычисления результатов фильтра: обычного выражения при рендере достаточно.

## Требования к сдаче

Все возможности ЛР1 сохранены; в интерфейсе есть работающие формы и интерактивные действия. Данные могут сбрасываться после перезагрузки — на этом этапе постоянное хранение не требуется. Преподаватель должен уметь проверить каждую операцию по отдельности и их сочетание.
