# Лабораторная работа №3. Приложение с API и маршрутизацией

## Постановка задачи

Развивайте интерфейс задач до небольшого клиентского приложения, способного получать данные с сервера и переходить между несколькими экранами.

Работа выполняется после изучения всех лекций, включая оптимизацию. Это заключительная лабораторная курса, а не отдельный итоговый проект.

## Требования

1. Используется React Router.
2. Созданы маршруты `/` (список задач), `/about` (информация о приложении) и `/tasks/:taskId` (детали задачи).
3. Есть навигация через `Link`.
4. Неизвестный маршрут показывает страницу «Не найдено».
5. Список загружается через Fetch API.
6. Во время запроса показывается состояние загрузки.
7. Сетевые и HTTP-ошибки показываются пользователю.
8. При пустом успешном ответе показывается отдельное сообщение.
9. Кнопка «Повторить» позволяет повторить неудачную загрузку.
10. URL API и сама функция запроса находятся в отдельном модуле.
11. При уходе со страницы запрос не должен пытаться обновлять уже неактуальный экран: используйте `AbortController` либо корректную проверку актуальности результата.
12. Страница деталей использует параметр `taskId` из URL.
13. Вёрстка адаптивна.
14. Выполнено профилирование интерфейса, после которого выбрана и обоснована одна оптимизация или обоснован отказ от неё.

## Учебный источник данных

Для GET-запросов допускается использовать [JSONPlaceholder](https://jsonplaceholder.typicode.com/). Например:

- список: `https://jsonplaceholder.typicode.com/todos?_limit=10`;
- одна запись: `https://jsonplaceholder.typicode.com/todos/1`.

Названия полей на сервере (`id`, `title`, `completed`) отличаются от поля `done`, использованного раньше. Обратите на это внимание при отображении.

Это учебный API: он не обеспечивает постоянное сохранение изменений. Поэтому не выдавайте отправку POST на JSONPlaceholder за полноценное долговременное создание данных. Обязательная часть этой лабораторной — получение и отображение информации, а не серверный CRUD.

## Порядок выполнения

1. Убедитесь, что предыдущая версия проекта запускается без ошибок.
2. Установите React Router через `npm install react-router`.
3. Разместите `BrowserRouter` вокруг корневого приложения.
4. Создайте компоненты страниц и настройте `Routes`/`Route`.
5. Создайте навигацию через `Link`.
6. Вынесите функцию GET-запроса в `api/tasks.js`.
7. На странице списка организуйте вызов загрузки при появлении страницы.
8. Отобразите loading/error/empty/success как разные состояния.
9. Добавьте возможность повторной загрузки кнопкой.
10. Добавьте ссылки на страницу каждой задачи и получите `taskId` через `useParams`.
11. Обрабатывайте несуществующий `taskId` отдельным сообщением.
12. Добавьте страницу 404 для неизвестных URL.
13. Проверьте прямую загрузку адресов и работу кнопки «Назад» браузера.
14. Проверьте интерфейс при отключённом интернете с помощью Network panel браузера.
15. Выполните `npm run build` и исправьте ошибки сборки.
16. Откройте React Profiler, зафиксируйте наблюдение за рендерами при одном действии. Если есть измеримая проблема, примените `memo`, `useMemo` или `useCallback` и повторите измерение; если нет, письменно объясните, почему оптимизация не требуется.

## Подсказки

Проверка успешности ответа:

```js
const response = await fetch(url);

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}

const data = await response.json();
```

Параметр адреса:

```js
const { taskId } = useParams();
```

Если сравниваете `taskId` с числовым полем объекта, учитывайте, что параметр URL приходит строкой.

## Ожидаемый результат

Пользователь открывает список, видит сообщение о загрузке и полученные задачи. По ссылке открывает детали одной задачи. При ошибке сети получает понятное сообщение и может повторить запрос. Переходы выполняются без полной перезагрузки страницы.

## Критерии проверки

- Все три названных маршрута работают.
- Неправильный маршрут отображает 404.
- GET-запрос и обработка ошибок корректны.
- Отдельно обрабатываются загрузка и пустой ответ.
- Код сетевого обращения не дублируется по компонентам.
- Нет нарушений правил хуков.
- Отмена/неактуальность запроса учитывается.
- Production build выполняется успешно.
- Есть измерение в Profiler и обоснованное решение об оптимизации.
