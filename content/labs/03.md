# Лабораторная работа №3. Маршруты, API и качество React-приложения

## Цель работы

Завершить приложение первых двух лабораторных работ: добавить маршрутизацию, асинхронную загрузку, обработку ошибок, уместное использование хуков, структуру файлов и обоснованную оценку производительности.

## Постановка задачи

Продолжайте **тот же проект** и **ту же предметную область**. Нельзя заменить работающий интерактивный каталог другим демонстрационным приложением. Необходимо сохранить добавление, редактирование, удаление, фильтр и сортировку из ЛР2, но добавить полноценную навигацию и данные, получаемые асинхронно.

## Исходные данные

Выполнены ЛР1 и ЛР2; изучены лекции 16–27. Установите `react-router` командой `npm install react-router`. Разрешено использовать публичный API либо локальный mock API. Полноценный сервер и база данных **не обязательны**.

## Единая модель проекта

Во всех вариантах предусмотрена коллекция однотипных объектов со стабильным `id`, компонент карточки, компонент списка, минимум два смысловых свойства для отображения и одно условное свойство для статуса. Студент выбирает предметную область **один раз** в первой лабораторной и продолжает **тот же проект** во второй и третьей, сохраняя данные, компоненты и CSS. Менять предметную область между работами нельзя без согласования с преподавателем.

Предметные различия не меняют объём обязательной реализации: каждый студент должен продемонстрировать сопоставимый набор механизмов React. Если в тематике нет естественного аналога корзины или избранного, используется действие «добавить в личный список / удалить из личного списка». Это действие не требует регистрации или серверной базы данных.

## Общие функциональные требования

1. Есть маршрут `/` с коллекцией и фильтрами, маршрут `/items/:itemId` с деталями выбранного объекта и маршрут `/about` с описанием приложения.
2. Переходы между внутренними экранами выполняются через `Link`; неизвестный маршрут показывает понятную страницу 404.
3. При открытии коллекции приложение асинхронно загружает начальные данные.
4. Отображаются разные состояния: загрузка, ошибка, успешный пустой результат, успешные данные.
5. При ошибке есть кнопка повторного получения данных.
6. При смене экрана или параметров старый асинхронный ответ не должен перезаписывать актуальные данные.
7. Страница детали получает `itemId` из URL и корректно показывает отсутствие записи.
8. Сохранены все операции из ЛР2. Локальные изменения не должны исчезать из-за случайного повторного GET-запроса при каждом рендере.
9. Есть одно обоснованное применение `useRef`, например фокус на поле поиска по кнопке «Найти».
10. Выделена повторяемая логика в пользовательский хук, **если** она действительно повторяется; иначе студент объясняет, почему искусственно создавать хук не нужно.
11. Проведена оценка производительности. При обнаружении затратного рендера или вычисления реализована и измерена подходящая оптимизация. Если проблемы нет, оформлен краткий аргументированный отказ от `memo`/`useMemo`/`useCallback`.
12. Приложение адаптивно и успешно собирается командой `npm run build`.

**Важно для публичных API:** не все сервисы позволяют редактировать и удалять свои данные или сохранять результаты. Если источник поддерживает только чтение, считайте API источником начальной коллекции, а все интерактивные изменения из ЛР2 выполняйте в локальном React-state. Не обещайте долговременное сохранение. У некоторых внешних сервисов могут измениться условия работы, форматы, ограничения частоты запросов; при недоступности используйте локальный mock API.

### Простой локальный mock API без backend-разработки

Создайте `public/mock/items.json` — массив минимум из 12 объектов вашей предметной области. Vite будет отдавать его по адресу `/mock/items.json`. Запрашивайте его через обычный `fetch('/mock/items.json')`. Чтобы **наблюдать** загрузку, в инструментах разработчика браузера можно ограничить скорость сети; не добавляйте искусственные задержки в производственную логику.

Это статический JSON, а не полноценный REST-сервер: он не сохраняет POST/PATCH/DELETE. Этого достаточно для обязательного GET-сценария и продолжения локальной интерактивности ЛР2. Допускается отдельно реализованный mock REST API, но писать сервер не требуется.

## Технические требования

- Маршрутизация через React Router и `BrowserRouter`.
- Fetch API с проверкой `response.ok`, обработкой исключений и чтением JSON.
- `useEffect` используется для синхронизации с внешним источником и имеет корректные зависимости и очистку.
- Для устаревших ответов предусмотрен `AbortController` или другой корректный механизм игнорирования.
- Модуль `api/items.js` отделён от компонентов; функции API возвращают данные либо выбрасывают ошибку.
- Для доступа к DOM в обоснованном месте используется `useRef`.
- Сложность компонентов сокращена разумной декомпозицией; прежняя функциональность не теряется.
- Оптимизация не является обязательной сама по себе: требуется решение, основанное на наблюдениях, а не формальное наличие хука.

## Методические указания

1. Сохраните рабочую версию ЛР2. Запишите список действий, которые уже работают; после каждого изменения сверяйтесь с ним.
2. Установите React Router и оберните `App` в `BrowserRouter` в `main.jsx`.
3. Добавьте страницу каталога, страницу деталей, страницу информации и 404. Не переносите весь существующий код сразу; сначала убедитесь, что текущий каталог работает внутри маршрута `/`.
4. Создайте `Link` из карточки на маршрут `/items/:itemId`, а в компоненте страницы используйте `useParams`. Учитывайте, что параметр маршрута — строка.
5. Выберите источник данных из таблицы. Если публичный API возвращает другую схему, создайте функцию нормализации объектов в единую структуру приложения.
6. Реализуйте функцию `getItems(signal)` в `api/items.js`. Внутри вызывайте `fetch`, проверяйте HTTP-статус и преобразуйте JSON. При необходимости проверяйте, что получен массив.
7. На странице каталога добавьте state загрузки, ошибки и данных. Реализуйте запрос в эффекте, который запускается, когда появляется экран, и корректно очищается.
8. Реализуйте повторную загрузку через явное действие пользователя: например, изменением счётчика попыток и зависимостью эффекта от него либо отдельной функцией с корректной отменой.
9. Убедитесь, что одновременные запросы не приводят к показу устаревшего результата. Проверьте быстрые переходы между экранами.
10. Сохраните создание и редактирование элементов из ЛР2 как локальные изменения над загруженной начальной коллекцией. Не перезаписывайте её фоновым GET на каждом вводе формы.
11. Добавьте один полезный сценарий с `useRef` — например, фокусировку строки поиска.
12. Если логика загрузки действительно дублируется на нескольких страницах, вынесите её в хук `useItems` или `useItem`. Если повторения нет, лучше оставить один аккуратный эффект и объяснить решение.
13. С помощью React DevTools/Profiler воспроизведите взаимодействие: поиск, фильтр, редактирование или прокрутку длинной коллекции. Определите, есть ли дорогое вычисление или компонент.
14. При измеренной проблеме примените уместное решение: `useMemo` для дорогой фильтрации, `memo` для дорогостоящей карточки со стабильными props либо `useCallback` при передаче обработчика memo-компоненту. Сравните поведение до и после. Если проблемы нет, не добавляйте хуки искусственно, а аргументируйте отказ.
15. Проверьте состояния loading/error/empty/success, кнопку повторной загрузки и неправильные URL. Выполните `npm run build`.

## Подсказки

Проверку HTTP-статуса не следует пропускать:

```js
const response = await fetch(url, { signal });
if (!response.ok) throw new Error(`Ошибка HTTP: ${response.status}`);
const data = await response.json();
```

При обработке ошибок отличайте пользовательскую ошибку от штатной отмены запроса через `AbortController`. Не запускайте POST-запросы из эффекта только ради демонстрации `useEffect`: действия, связанные с кнопкой или формой, обычно выполняют в обработчике события.
