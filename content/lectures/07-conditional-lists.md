# Условия и списки

## Создание элементов из массива

У нас уже есть массивы и метод `map`. В React `map` часто превращает элементы данных в JSX-элементы.

`src/App.jsx`:

```jsx
import TaskCard from './TaskCard.jsx';

const tasks = [
  { id: 1, title: 'HTML', done: true },
  { id: 2, title: 'React', done: false }
];

export default function App() {
  return (
    <main>
      <h1>Мои задачи</h1>
      {tasks.map((task) => (
        <TaskCard
          key={task.id}
          title={task.title}
          done={task.done}
        />
      ))}
    </main>
  );
}
```

`map` создаёт массив React-элементов. React отображает каждый элемент. `key` — специальный идентификатор, который помогает React сопоставить элементы списка между обновлениями. Он должен быть стабильным и уникальным среди соседних элементов: `id` подходит, случайное число на каждом рендере — нет.

`key` не поступает в обычные props компонента. Если ребёнку нужен `id`, его передают отдельно: `id={task.id}`.

## Когда список пуст

Пользователь должен видеть понятное сообщение вместо пустой области:

```jsx
export default function App() {
  const tasks = [];

  if (tasks.length === 0) {
    return <p>Задач пока нет.</p>;
  }

  return <p>Всего задач: {tasks.length}</p>;
}
```

Проверка выполняется до основного JSX. Это **условный рендеринг** — выбор отображаемого содержимого на основании данных.

Можно использовать ранее изученный тернарный оператор:

```jsx
<p>{tasks.length === 0 ? 'Нет задач' : `Задач: ${tasks.length}`}</p>
```

Обратные кавычки создают **шаблонную строку**. Внутри `${...}` вставляется значение JavaScript. Обычные кавычки такого синтаксиса не поддерживают.

Мы теперь умеем строить интерфейс из массива и показывать разные сообщения в зависимости от данных. Этого достаточно для первой лабораторной.


## Зачем key сохраняется между обновлениями

Представьте список из трёх задач. После удаления первой оставшиеся сдвигаются. Если использовать индекс `0, 1, 2` в качестве `key`, React может ошибочно сопоставить состояние старой карточки с другой задачей. Уникальный идентификатор сущности остаётся с ней даже после перемещения и удаления. Поэтому `key={task.id}` обычно правильнее `key={index}`.

При этом `key` не обязателен для всякого одиночного элемента. Он важен там, где React необходимо различать соседние элементы или намеренно сбрасывать состояние конкретной ветви дерева.

## Правильный key — не номер строки на экране

Представьте список из трёх задач, где каждая карточка позднее получит локальное состояние «раскрыта ли подробная информация». Если использовать индекс массива как `key`, при удалении первой задачи индексы оставшихся элементов изменятся. React может сопоставить старое локальное состояние с другой карточкой. Стабильный идентификатор `task.id` не имеет этой проблемы.

`key` нужен React при **согласовании** (сопоставлении старых и новых элементов). Он не передаётся ребёнку как обычный prop. Если карточке требуется идентификатор для действий пользователя, передайте `id={task.id}` отдельно.

## Условное отсутствие элемента

JSX допускает `null`: компонент, вернувший `null`, ничего не добавляет в DOM. Это удобно для необязательного блока, но не должно заменять понятное сообщение об отсутствии данных, когда пользователь ожидает список. При проверке `tasks.length > 0 && <List />` следите, чтобы слева стояло именно логическое выражение: запись `tasks.length && <List />` для пустого массива может вывести `0`.

**Наблюдаемый результат:** массив управляет количеством карточек; `key` сохраняет их идентичность; условие выбирает между списком и сообщением. Это основа первой лабораторной.
