# Как React обновляет интерфейс

## Что запускает повторный рендер

React сначала отображает приложение. Позже React может снова вызвать компонент, когда изменится его состояние, обновится родитель или изменится контекст. Это **повторный рендер**. Такой вызов ещё не означает, что браузер изменит DOM.

Полезно разделять три шага:

1. **Trigger** — появилось основание для обновления, например вызов setter состояния.
2. **Render phase** — React вызывает компоненты и вычисляет новое описание интерфейса.
3. **Commit phase** — React применяет необходимые изменения к DOM.

Фаза рендера должна оставаться чистой: React может вызывать её повторно, в том числе чтобы проверить код в режиме разработки.

## Пример без изменения DOM

```jsx
function Greeting({ name }) {
  console.log('Компонент вызван');
  return <p>Привет, {name}</p>;
}
```

Если родитель отобразился повторно и `name` остался тем же, React может снова вызвать `Greeting`, но текст `<p>` в DOM уже правильный, поэтому менять его не требуется. Сообщение в консоли показывает факт выполнения компонента, а не факт изменения DOM.

## Reconciliation — сопоставление описаний

**Согласование** (*reconciliation*) — процесс, в ходе которого React определяет, какие части нового дерева соответствуют предыдущему дереву. На совпадение влияют тип элемента и его положение в дереве, а для списка — `key`.

Это концептуальная модель поведения React, а не обещание конкретного внутреннего алгоритма при любой версии. Для разработчика важны предсказуемые последствия: одинаковая компонента на том же месте обычно сохраняет состояние, другой тип элемента или другой `key` может привести к созданию компонента заново.

Источник: [Render and Commit](https://react.dev/learn/render-and-commit).

## Наблюдаем отдельно рендер и изменение DOM

Полный пример для `src/App.jsx` (замените содержимое файла):

```jsx
import { useState } from 'react';

function Label({ text }) {
  console.log('Render Label:', text);
  return <p>{text}</p>;
}

export default function App() {
  const [clicks, setClicks] = useState(0);
  console.log('Render App:', clicks);
  return (
    <main>
      <button onClick={() => setClicks((n) => n + 1)}>
        Нажатий: {clicks}
      </button>
      <Label text="Постоянная подпись" />
    </main>
  );
}
```

При клике React вызывает `App` повторно; без мемоизации он может вызвать и `Label`, несмотря на прежний prop `text`. В консоли появится сообщение о вызове функции. Но `<p>Постоянная подпись</p>` не нужно менять в DOM: значение текста не изменилось. Это пример различия **render phase** (вычисление описания) и **commit phase** (применение изменений). В StrictMode сообщений в режиме разработки может быть больше.

## Какие обновления React может пропустить

Если вызвать setter с тем же значением и React сочтёт значения равными по `Object.is`, он может пропустить обновление потомков. Это не значит, что нужно вручную выбирать DOM-узлы и менять текст: согласование остаётся задачей React.

**Сбойный подход:** менять DOM через `document.querySelector(...).textContent` для содержимого, которое уже выводит React. При следующем React-обновлении ручное изменение может быть перезаписано. Управляйте такими значениями через state и props.
