# Когда нужен React.memo

## Повторный рендер не всегда проблема

Когда родитель отображается снова, дочерние компоненты тоже могут вызываться. Это нормально. React может не менять DOM, если итоговое описание не изменилось. Замедление возникает, когда вычисления действительно дороги или большая часть дерева обновляется без полезной работы.

**Профилирование** — измерение того, где программа тратит время. React Developer Tools содержит **Profiler**, показывающий стоимость рендеров. Сначала изучите реальную проблему; не добавляйте оптимизации по привычке.

## Что делает React.memo

`memo` — функция React, создающая компонент, который обычно пропускает повторный рендер при неизменных props.

```jsx
import { memo, useState } from 'react';

const Label = memo(function Label({ title }) {
  console.log('Label render');
  return <p>{title}</p>;
});

export default function App() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount((x) => x + 1)}>{count}</button>
      <Label title="Постоянный заголовок" />
    </>
  );
}
```

При увеличении `count` родитель обновляется. Значение `title` остаётся тем же, и `memo` может пропустить рендер `Label`. Но это **оптимизация, а не гарантия**, а при таком маленьком компоненте её выгода практически отсутствует. В development Strict Mode могут появиться дополнительные вызовы, поэтому измеряйте производительность в подходящих условиях.

## Ссылочная идентичность

JavaScript сравнивает простые значения и объекты по-разному:

```js
console.log(2 === 2); // true
console.log({ x: 1 } === { x: 1 }); // false
```

Два отдельных объекта имеют разные ссылки. Если передавать `options={{ color: 'red' }}` в memo-компонент при каждом рендере, это новый объект, хотя содержимое выглядит одинаково. Аналогичная ситуация с функциями, которые создаются во время рендера.

`memo` не отменяет обновления собственного state компонента или контекста, который он использует. Он не является способом предотвратить корректные обновления интерфейса.

Документация: [memo](https://react.dev/reference/react/memo).

## Измеряем проблему до оптимизации

Пусть родительский компонент меняет текст поискового поля, а рядом находится тяжёлая карточка со сложной диаграммой. При каждом изменении state родителя React обычно снова вычисляет и дочерний компонент. Если карточка действительно долго рендерится и её props не изменились, можно рассмотреть `memo`.

```jsx
import { memo, useState } from 'react';

const StaticCard = memo(function StaticCard({ title }) {
  console.log('Render StaticCard');
  return <p>{title}</p>;
});

export default function App() {
  const [query, setQuery] = useState('');
  return (
    <>
      <input value={query} onChange={(event) => setQuery(event.target.value)} />
      <StaticCard title="Неизменная карточка" />
    </>
  );
}
```

В обычном режиме React сравнивает props `StaticCard` и может пропустить повторное вычисление карточки, когда `query` изменяется, а `title` нет. `memo` **не гарантирует**, что компонент никогда не будет вызван: его собственный state или используемый Context могут измениться, а React сохраняет право на повторную работу.

## Почему объектные props могут всё испортить

Объекты сравниваются по ссылке, а не по совпадению полей: `{ value: 1 } !== { value: 1 }`. Если родитель на каждом рендере передаёт `options={{color:'red'}}`, новый объект будет отличаться от предыдущего. Иногда правильнее передать примитивный prop `color="red"`, чем сразу добавлять `useMemo`. Оптимизация начинается с простого интерфейса props.
